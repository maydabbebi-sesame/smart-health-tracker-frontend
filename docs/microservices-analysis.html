SmartHealth — Is this a Microservices Architecture?

Analysis of smart-health-tracker-frontend together with backend/api and mediassist_service

Verdict: No. The system is a modular monolith (backend/api) plus a tightly-coupled satellite service (mediassist_service) that share a single MySQL database, called directly from a single-page frontend. This pattern is often called a "distributed monolith" — arguably worse than a clean monolith, since it has network calls without the isolation benefits microservices are supposed to provide.

What actually exists

ComponentWhat it actually is
smart-health-tracker-frontend One React/Vite SPA, calling two hardcoded base URLs (VITE_API_BASE_URL, VITE_MEDIASSIST_URL) — see src/services/apiClient.js and src/services/mediAssistService.js.
backend/api One Flask process (app_backend.py) registering 11 blueprints — users, auth, doctors, appointments, vitals, alerts, medical_history, vaccinations, admin, translations, forms — all in one codebase, one deploy unit, one shared mysql.connector connection to a single smarthealth database.
mediassist_service A second Flask process (port 5001) for the LLM symptom-analysis chat relay.

Why mediassist_service doesn't count as a real microservice either

It reads backend/api/.env directly and connects to the same MySQL database (app.py), querying tables like mediassist_history that the main backend owns. It even copy-pastes the auth-token decoding logic from backend/api/security.py instead of calling an endpoint — the code itself admits this:

"Duplicated from security.py's decode_id rather than imported because mediassist_service is a standalone Flask app with no dependency on the backend/api package; keep the two in sync if either changes."

That's the textbook anti-pattern microservices are designed to avoid: shared database + duplicated logic instead of a contract-based API call between services.

What's missing to call this microservices

  • missingDatabase-per-service — both backend processes share one MySQL schema; no service exclusively owns its data.
  • missingIndependent deployability per domain — backend/api is one deployable unit for 11 business domains; shipping a change to one means redeploying all of them.
  • missingService-to-service contracts — mediassist_service talks to the DB and duplicates auth code instead of calling backend/api's endpoints over HTTP/gRPC.
  • missingAPI gateway / service discovery — the frontend hardcodes two localhost ports; there's no routing layer, load balancer, or registry.
  • missingContainerization / orchestration — no Dockerfile, docker-compose, or Kubernetes manifests anywhere in the repo.
  • missingResilience patterns — no retries, timeouts, circuit breakers, or health checks between the two Python processes.
  • missingIndependent scaling / tech-stack isolation — both processes are Flask + mysql-connector; nothing is built to scale or evolve independently.
  • missingDistributed observability — no correlation IDs or tracing tying a frontend request across both backends.

Distributed monolith is the most accurate label today.

A real split would mean extracting domains like auth, vitals, and appointments into independently deployable services behind a gateway, giving each its own datastore, and having mediassist_service call backend/api's API instead of reaching into its database directly.
