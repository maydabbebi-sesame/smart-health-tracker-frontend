1. Architecture overview

SmartHealth uses a microservices architecture: the backend is split into five independently deployable Flask services, each with its own scoped MySQL credentials and its own area of responsibility. All traffic from the frontend passes through a single nginx gateway on port 8080, which routes each request by URL path prefix to the correct service. A RabbitMQ event bus handles asynchronous cross-service notifications (e.g. an appointment confirmation creating an in-app alert).

Shared auth library (libs/sh_common)

All five services import a shared Python package (libs/sh_common) that provides: JWT issuance and verification, the HMAC-based public UID scheme (encode_id / decode_id), the token_required / roles_required decorators, email utilities, and the RabbitMQ publish_event / consume_events helpers. Each service verifies JWTs locally using the shared SECRET_KEY — no network call to auth-service is needed per request.

2. Services reference

auth-service
:5101 — /api/auth/*
Login, registration, email verification, MFA, OAuth (Google/Facebook/Apple), JWT issuance, password reset, logout.
users-service
:5102 — /api/users/*, /api/admin/*, /api/medical-history/*, /api/vaccinations/*, /api/translations/*, /uploads/*
User profiles, admin management, medical history, vaccinations, i18n translations, profile picture uploads. Admin statistics endpoint fans out to health-data and doctors-appointments services.
health-data-service
:5103 — /api/vitals/*, /api/forms/*, /api/alerts/*
Vital signs recording, health forms, in-app alerts. Vitals and forms trigger alerts in-process. Receives appointment lifecycle events from RabbitMQ and creates in-app alerts.
health-data-worker
no HTTP port — background process
RabbitMQ consumer. Listens for appointment.* events published by doctors-appointments-service and inserts in-app alert rows into the alerts table.
doctors-appointments-service
:5104 — /api/doctors/*, /api/appointments/*
External doctors directory (platform, med.tn, OSM), appointment booking, availability, ratings. Publishes appointment events to RabbitMQ.
mediassist-service
:5001 — /api/mediassist/*
LLM chat relay for symptom analysis, trend analysis, Doctor Agent decisions, recommendation history.

4. Setup on a new machine

One-time requirement on the original machine: you need to export the database as a SQL dump before setting up elsewhere. If you already have backend/database/docker-init/01-dump.sql from the original machine, copy it to the same path on the new machine and skip Step 2.

Step-by-step

  1. Clone the repository 
    git clone <repository-url>
cd smart-health-tracker-frontend
  2. Generate the database dump (original machine only, requires local MySQL)
    On Windows (PowerShell) — use --result-file to avoid UTF-16 encoding issues: 
    & "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysqldump.exe" `
    -u smarthealth -pTest12#### `
    --result-file="backend/database/docker-init/01-dump.sql" `
    smarthealth
    On macOS / Linux: 
    mysqldump -u smarthealth -p smarthealth \
    > backend/database/docker-init/01-dump.sql

    This file is git-ignored (contains real user data). Copy it to the same path on the new machine via USB, SCP, or any file transfer tool.

  3. Install frontend dependencies 
    npm install
  4. Configure environment variables
    The root .env already has the correct Docker gateway settings. No edits needed unless you want to use real SMTP or a different Google Client ID. See Section 5 for a full reference.
  5. Build and start all services 
    docker compose up --build

    First run takes 5–10 minutes: it downloads the base images, builds 5 service images, seeds MySQL from the dump, creates the per-service DB accounts, and starts everything. Subsequent runs are much faster (cached layers).

    When ready, you will see all services printing their startup lines:

    auth-service-1         | * Running on http://0.0.0.0:5101
users-service-1        | * Running on http://0.0.0.0:5102
health-data-service-1  | * Running on http://0.0.0.0:5103
doctors-...-service-1  | * Running on http://0.0.0.0:5104
mediassist-service-1   | * Running on http://0.0.0.0:5001
  6. Verify all containers are healthy 
    docker compose ps
    All 9 entries should show Up or Up (healthy). If any show Exit, run docker compose logs <service-name> to diagnose.
  7. Start the frontend dev server 
    npm run dev
    Open http://localhost:5173 in your browser.
Quick smoke test: open http://localhost:8080/api/translations/en in a browser. If it returns a JSON object with translation keys, the gateway, users-service, and MySQL are all working correctly.

Stopping and restarting

# Stop all containers (data is preserved in the mysql_data volume)
docker compose down

# Start again (no rebuild needed unless code changed)
docker compose up

# Rebuild after code changes
docker compose up --build

# Full reset — deletes all data and starts from the dump again
docker compose down -v
docker compose up --build

6. Accessing the database with MySQL Workbench

The Docker MySQL is mapped to host port 3307 (not 3306) to avoid conflicting with any locally installed MySQL instance.

Create a new connection

  1. Open MySQL Workbench and click the + icon next to "MySQL Connections".
  2. Fill in the connection details:
    FieldValue
    Connection NameSmartHealth Docker
    Connection MethodStandard (TCP/IP)
    Hostname127.0.0.1
    Port3307
    Usernameroot
    Passwordroot_pw_2026 (click "Store in Vault")
    Default Schemasmarthealth
  3. Click Test Connection. You should see "Successfully made the MySQL connection".
  4. Click OK, then double-click the connection to open it.

Connecting as a service account (to test grants)

You can create additional Workbench connections using each service's own restricted account to verify that DB isolation is working correctly. For example, connecting as healthdata_svc / healthdata_svc_pw_2026 lets you confirm it can read vitals but cannot see appointments or users.password.

Docker must be running (docker compose up) for Workbench to connect. If Docker is stopped, port 3307 is closed and the connection will fail.

7. Running in development mode (without Docker)

If Docker is not available, you can run each service directly with Python, using your local MySQL. Every service has its own .env file pre-configured for local dev. 

# Terminal 1 — auth-service
cd services/auth-service
python app.py   # listens on :5101

# Terminal 2 — users-service
cd services/users-service
python app.py   # listens on :5102

# Terminal 3 — health-data-service (HTTP API)
cd services/health-data-service
python app.py   # listens on :5103

# Terminal 4 — health-data-worker (RabbitMQ consumer)
cd services/health-data-service
python worker.py

# Terminal 5 — doctors-appointments-service
cd services/doctors-appointments-service
python app.py   # listens on :5104

# Terminal 6 — mediassist-service
cd mediassist_service
python app.py   # listens on :5001

In development mode, the frontend .env should point directly at the legacy monolith or at the individual service ports. The nginx gateway is only active inside Docker Compose.

RabbitMQ must be installed and running locally for the appointment → alert event flow to work in dev mode. The default connection is localhost:5672 with credentials guest / guest.

8. Troubleshooting

502 Bad Gateway from nginx

The gateway is running but can't reach an upstream service.

  • Run docker compose ps — any service not showing Up is the culprit.
  • Run docker compose logs <service-name> to see the startup error.
  • The Flask app inside the container must listen on 0.0.0.0, not 127.0.0.1. Check that each app.run() call includes host="0.0.0.0".

Access denied for user '…_svc'@'...'

The per-service MySQL accounts don't exist — the init scripts didn't run.

  • This happens when the MySQL volume already has data from a previous run. The docker-entrypoint-initdb.d scripts only execute on a fresh (empty) volume.
  • Fix: docker compose down -v && docker compose up --build
  • Also make sure 01-dump.sql was generated with --result-file, not with PowerShell's > redirect (which produces UTF-16 encoding that MySQL cannot parse).

Port 3306 already in use

A locally installed MySQL is already using port 3306. The Docker MySQL is mapped to 3307 to avoid this conflict — no action needed.

Port 5672 already in use

A locally installed RabbitMQ is already running. Either stop it or change the host port in docker-compose.yml: "5673:5672".

Build fails with "no such file or directory: gcc"

A package (typically pycairo via reportlab) needs a C compiler. All Dockerfiles use FROM python:3.11 (full image with build tools) — make sure no Dockerfile accidentally uses python:3.11-slim.

MySQL init script fails with "ASCII '\0' appeared in the statement"

The 01-dump.sql was saved as UTF-16 (PowerShell's default for > redirects). Regenerate it using --result-file as shown in Section 4, Step 2.

Checking which users exist in the Docker MySQL

docker exec smart-health-tracker-frontend-mysql-1 \
    mysql -uroot -proot_pw_2026 \
    -e "SELECT user, host FROM mysql.user WHERE user LIKE '%_svc';"

You should see all five service accounts (auth_svc, users_svc, healthdata_svc, doctorsappt_svc, mediassist_svc).
