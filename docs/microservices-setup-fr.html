1. Vue d'ensemble de l'architecture

SmartHealth utilise une architecture microservices : le backend est découpé en cinq services Flask déployables indépendamment, chacun disposant de ses propres identifiants MySQL restreints et de son propre domaine de responsabilité. Tout le trafic en provenance du frontend passe par un unique gateway nginx sur le port 8080, qui achemine chaque requête vers le bon service selon le préfixe d'URL. Un bus d'événements RabbitMQ gère les notifications asynchrones entre services (par exemple, la confirmation d'un rendez-vous génère une alerte in-app). 

  Frontend React (npm run dev → :5173)
        │
        └── http://localhost:8080  (gateway nginx)
                  │
    ┌─────────────┼──────────────────────────────────┐
    │             │              │                   │
    ▼             ▼              ▼                   ▼
auth-service  users-service  health-data-service  doctors-appointments-service
  :5101          :5102            :5103                    :5104
                                  │
                            health-data-worker  ← RabbitMQ ← doctors-appt-service
                                  │
                         mediassist-service :5001
                  │
        ┌─────────┴──────────┐
        ▼                    ▼
     MySQL :3307         RabbitMQ :5672
  (comptes par service)  (interface de gestion :15672)

Bibliothèque d'authentification partagée (libs/sh_common)

Les cinq services importent un package Python partagé (libs/sh_common) qui fournit : l'émission et la vérification des JWT, le schéma d'identifiants publics basé sur HMAC (encode_id / decode_id), les décorateurs token_required / roles_required, les utilitaires d'envoi d'e-mail, ainsi que les helpers RabbitMQ publish_event / consume_events. Chaque service vérifie les JWT localement grâce à la SECRET_KEY partagée — aucun appel réseau vers auth-service n'est nécessaire par requête.

2. Référence des services

auth-service
:5101 — /api/auth/*
Connexion, inscription, vérification d'e-mail, MFA, OAuth (Google/Facebook/Apple), émission de JWT, réinitialisation de mot de passe, déconnexion.
users-service
:5102 — /api/users/*, /api/admin/*, /api/medical-history/*, /api/vaccinations/*, /api/translations/*, /uploads/*
Profils utilisateurs, gestion administrative, historique médical, vaccinations, traductions i18n, téléversement de photos de profil. L'endpoint des statistiques admin agrège les données des autres services.
health-data-service
:5103 — /api/vitals/*, /api/forms/*, /api/alerts/*
Enregistrement des constantes vitales, formulaires de santé, alertes in-app. Les constantes et formulaires déclenchent des alertes en interne. Reçoit les événements de rendez-vous via RabbitMQ et crée des alertes in-app.
health-data-worker
aucun port HTTP — processus en arrière-plan
Consommateur RabbitMQ. Écoute les événements appointment.* publiés par doctors-appointments-service et insère des lignes d'alerte dans la table alerts.
doctors-appointments-service
:5104 — /api/doctors/*, /api/appointments/*
Annuaire des médecins (plateforme, med.tn, OSM), prise de rendez-vous, disponibilités, évaluations. Publie des événements de rendez-vous vers RabbitMQ.
mediassist-service
:5001 — /api/mediassist/*
Relais de chat LLM pour l'analyse des symptômes, l'analyse des tendances, les décisions de l'Agent Médecin et l'historique des recommandations.

4. Installation sur une nouvelle machine

Prérequis unique sur la machine d'origine : vous devez exporter la base de données sous forme de dump SQL avant toute installation ailleurs. Si vous disposez déjà de backend/database/docker-init/01-dump.sql depuis la machine d'origine, copiez-le au même chemin sur la nouvelle machine et passez directement à l'étape 3.

Procédure pas à pas

  1. Cloner le dépôt 
    git clone <url-du-dépôt>
cd smart-health-tracker-frontend
  2. Générer le dump de la base de données (machine d'origine uniquement, MySQL local requis)
    Sous Windows (PowerShell) — utiliser --result-file pour éviter les problèmes d'encodage UTF-16 : 
    & "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysqldump.exe" `
    -u smarthealth -pTest12#### `
    --result-file="backend/database/docker-init/01-dump.sql" `
    smarthealth
    Sous macOS / Linux : 
    mysqldump -u smarthealth -p smarthealth \
    > backend/database/docker-init/01-dump.sql

    Ce fichier est ignoré par Git (il contient des données réelles). Transférez-le vers le même chemin sur la nouvelle machine via clé USB, SCP ou tout autre outil de transfert.

  3. Installer les dépendances du frontend 
    npm install
  4. Configurer les variables d'environnement
    Le fichier .env à la racine contient déjà les paramètres corrects pour le gateway Docker. Aucune modification n'est nécessaire sauf si vous souhaitez utiliser un vrai serveur SMTP ou un autre Google Client ID. Voir Section 5 pour la référence complète.
  5. Construire et démarrer tous les services 
    docker compose up --build

    Le premier lancement prend 5 à 10 minutes : téléchargement des images de base, construction des 5 images de services, initialisation de MySQL depuis le dump, création des comptes DB par service, démarrage de tout l'environnement. Les lancements suivants sont beaucoup plus rapides (couches en cache).

    Lorsque tout est prêt, vous verrez les lignes de démarrage de chaque service :

    auth-service-1         | * Running on http://0.0.0.0:5101
users-service-1        | * Running on http://0.0.0.0:5102
health-data-service-1  | * Running on http://0.0.0.0:5103
doctors-...-service-1  | * Running on http://0.0.0.0:5104
mediassist-service-1   | * Running on http://0.0.0.0:5001
  6. Vérifier que tous les conteneurs sont en bonne santé 
    docker compose ps
    Les 9 entrées doivent afficher Up ou Up (healthy). Si l'une affiche Exit, exécutez docker compose logs <nom-du-service> pour diagnostiquer.
  7. Démarrer le serveur de développement frontend 
    npm run dev
    Ouvrez http://localhost:5173 dans votre navigateur.
Test rapide de bon fonctionnement : ouvrez http://localhost:8080/api/translations/en dans un navigateur. Si la réponse est un objet JSON contenant des clés de traduction, le gateway, le users-service et MySQL fonctionnent correctement.

Arrêter et redémarrer

# Arrêter tous les conteneurs (les données sont conservées dans le volume mysql_data)
docker compose down

# Redémarrer (sans reconstruction sauf si le code a changé)
docker compose up

# Reconstruire après des modifications du code
docker compose up --build

# Remise à zéro complète — supprime toutes les données et repart du dump
docker compose down -v
docker compose up --build

6. Accès à la base de données avec MySQL Workbench

Le MySQL Docker est mappé sur le port hôte 3307 (et non 3306) afin d'éviter tout conflit avec une éventuelle instance MySQL installée localement.

Créer une nouvelle connexion

  1. Ouvrir MySQL Workbench et cliquer sur l'icône + à côté de "MySQL Connections".
  2. Renseigner les paramètres de connexion :
    ChampValeur
    Connection NameSmartHealth Docker
    Connection MethodStandard (TCP/IP)
    Hostname127.0.0.1
    Port3307
    Usernameroot
    Passwordroot_pw_2026 (cliquer sur "Store in Vault")
    Default Schemasmarthealth
  3. Cliquer sur Test Connection. Le message "Successfully made the MySQL connection" doit s'afficher.
  4. Cliquer sur OK, puis double-cliquer sur la connexion pour l'ouvrir.

Connexion avec un compte de service (pour tester les restrictions)

Vous pouvez créer des connexions Workbench supplémentaires en utilisant le compte restreint de chaque service afin de vérifier que l'isolation de la base de données fonctionne correctement. Par exemple, se connecter en tant que healthdata_svc / healthdata_svc_pw_2026 permet de confirmer que ce compte peut lire vitals mais ne peut pas accéder à appointments ni à users.password.

Docker doit être en cours d'exécution (docker compose up) pour que Workbench puisse se connecter. Si Docker est arrêté, le port 3307 est fermé et la connexion échouera.

7. Mode développement (sans Docker)

Si Docker n'est pas disponible, vous pouvez exécuter chaque service directement avec Python en utilisant votre MySQL local. Chaque service possède son propre fichier .env préconfiguré pour le développement local. 

# Terminal 1 — auth-service
cd services/auth-service
python app.py   # écoute sur :5101

# Terminal 2 — users-service
cd services/users-service
python app.py   # écoute sur :5102

# Terminal 3 — health-data-service (API HTTP)
cd services/health-data-service
python app.py   # écoute sur :5103

# Terminal 4 — health-data-worker (consommateur RabbitMQ)
cd services/health-data-service
python worker.py

# Terminal 5 — doctors-appointments-service
cd services/doctors-appointments-service
python app.py   # écoute sur :5104

# Terminal 6 — mediassist-service
cd mediassist_service
python app.py   # écoute sur :5001

En mode développement, le fichier .env du frontend doit pointer directement vers le monolithe legacy ou vers les ports individuels des services. Le gateway nginx n'est actif qu'à l'intérieur de Docker Compose.

RabbitMQ doit être installé et en cours d'exécution localement pour que le flux rendez-vous → alerte fonctionne en mode développement. La connexion par défaut est localhost:5672 avec les identifiants guest / guest.

8. Résolution des problèmes

502 Bad Gateway depuis nginx

Le gateway fonctionne mais ne peut pas atteindre un service en amont.

  • Exécuter docker compose ps — tout service n'affichant pas Up est le coupable.
  • Exécuter docker compose logs <nom-du-service> pour voir l'erreur de démarrage.
  • L'application Flask à l'intérieur du conteneur doit écouter sur 0.0.0.0 et non 127.0.0.1. Vérifier que chaque appel app.run() contient host="0.0.0.0".

Accès refusé pour l'utilisateur '…_svc'@'...'

Les comptes MySQL par service n'existent pas — les scripts d'initialisation ne se sont pas exécutés.

  • Cela se produit lorsque le volume MySQL contient déjà des données d'un lancement précédent. Les scripts de docker-entrypoint-initdb.d ne s'exécutent que sur un volume vierge.
  • Solution : docker compose down -v && docker compose up --build
  • S'assurer également que 01-dump.sql a été généré avec --result-file et non avec le redirect > de PowerShell (qui produit un encodage UTF-16 illisible par MySQL).

Port 3306 déjà utilisé

Un MySQL installé localement utilise déjà le port 3306. Le MySQL Docker est mappé sur le port 3307 pour éviter ce conflit — aucune action n'est requise.

Port 5672 déjà utilisé

Un RabbitMQ installé localement est déjà en cours d'exécution. Arrêtez-le ou modifiez le port hôte dans docker-compose.yml : "5673:5672".

La construction échoue avec "no such file or directory: gcc"

Un package (généralement pycairo via reportlab) nécessite un compilateur C. Tous les Dockerfiles utilisent FROM python:3.11 (image complète avec les outils de compilation) — vérifier qu'aucun Dockerfile n'utilise accidentellement python:3.11-slim.

Le script d'initialisation MySQL échoue avec "ASCII '\0' appeared in the statement"

Le fichier 01-dump.sql a été enregistré en UTF-16 (encodage par défaut du redirect > de PowerShell). Régénérez-le avec --result-file comme indiqué à la Section 4, Étape 2.

Vérifier les utilisateurs présents dans le MySQL Docker

docker exec smart-health-tracker-frontend-mysql-1 \
    mysql -uroot -proot_pw_2026 \
    -e "SELECT user, host FROM mysql.user WHERE user LIKE '%_svc';"

Vous devriez voir les cinq comptes de service (auth_svc, users_svc, healthdata_svc, doctorsappt_svc, mediassist_svc).
