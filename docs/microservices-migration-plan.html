SmartHealth — Migration to Microservices

Implementation plan, derived from microservices-analysis.html

Context

The current backend is a modular monolith: backend/api/app_backend.py is one Flask process registering 11 blueprints (auth, users, doctors, appointments, vitals, alerts, forms, admin, translations, medical_history, vaccinations), all sharing one MySQL connection and one database (smarthealth). A second process, mediassist_service/app.py, makes things worse: it connects to the same database directly and duplicates the auth-token decoding logic from backend/api/security.py instead of calling an API — a "distributed monolith," not microservices.

This plan is scoped for a 2nd-year PFA project. Chosen parameters:

Granularity5 services + gateway
OrchestrationDocker Compose
Inter-service commsRabbitMQ + sync REST
Data ownershipOne MySQL instance, per-service DB users/grants

Every service is its own Flask app (reuses the existing Flask/MySQL skill already in the codebase — no new language/framework introduced), its own Dockerfile, its own requirements.txt, and is registered as its own entry in docker-compose.yml.

Shared library: libs/sh_common

Extracted from backend/api/security.py + the auth bits of config.py:

  • encode_id / decode_id (HMAC UID scheme) — currently security.py:13-29.
  • token_required / roles_required decorators — currently auth.py:212-268, imported by every blueprint today; becomes a library that verifies the JWT signature locally with the shared JWT_SECRET_KEY.
  • The publicize_* functions (security.py:32-256) move with the data they format — e.g. publicize_vital → health-data-service, publicize_appointment → doctors-appointments-service.

Each service installs sh_common as a local path dependency in Compose. This directly replaces what mediassist_service/app.py:78-86 currently does by copy-pasting decode_id — its own comment ("keep the two in sync if either changes") is exactly the smell this library removes.

Messaging (RabbitMQ)

Only used for genuine cross-service events — not for vitals/forms→alerts, since that coupling disappears once they're co-located.

One topic exchange (smarthealth.events) via pika is enough at this scale.

Database approach

  1. Create one DB user per service (auth_svc, users_svc, healthdata_svc, doctorsappt_svc, mediassist_svc) via a new migration backend/database/migrations/026_create_service_db_users.sql.
  2. GRANT SELECT, INSERT, UPDATE, DELETE only on the tables each service owns. E.g. healthdata_svc can't query users or appointments even though they're in the same schema.
  3. doctors-appointments-service gets read-only (SELECT) access to users to resolve name/email for confirmation messages.
  4. Each service's config.py gets its own DB credentials env vars — no more one shared DB_CONFIG for every process.

This enforces "no service reaches into another's tables" without paying for N database containers.

Docker Compose

New top-level docker-compose.yml with: mysql, rabbitmq, auth-service, users-service, health-data-service, doctors-appointments-service, mediassist-service, gateway. Each service folder gets its own small Dockerfile (python:3.11-slim + pip install -r requirements.txt + flask run/gunicorn). Frontend keeps running with npm run dev outside Compose, pointed at the gateway's exposed port.

Migration order (strangler fig — verify after each phase)

1Extract libs/sh_common from security.py + the decorator/JWT logic in auth.py, without changing topology yet. Run backend/api/test_auth_flow.py to confirm zero behavior change.
2Stand up the gateway + Compose in front of the still-monolithic backend/api (renamed legacy-monolith) and point the frontend at the gateway. Confirms routing/Compose work before any split.
3Extract auth-service (smallest blast radius; everyone else depends on it). Update gateway routes for /api/auth/*.
4Extract users-service (users.py, admin.py, medical_history.py, vaccinations.py, translations.py, /uploads). Apply the users_svc DB grants.
5Extract health-data-service (vitals.py, forms.py, alerts.py). insert_alert stays an in-process call inside the new service.
6Extract doctors-appointments-service (doctors.py, appointments.py). Add the RabbitMQ publisher for appointment events; health-data-service adds the consumer.
7Refactor mediassist_service to use sh_common instead of its duplicated _decode_user_id, get its own DB grants, optionally publish mediassist.recommendation.flagged.
8Decommission backend/api/app_backend.py once all 11 blueprints have moved out; delete the legacy-monolith Compose entry.

Verification per phase

  • Each service keeps/moves the relevant existing tests (test_api.py, test_auth_flow.py) and the Postman collection — update base URLs to the gateway and re-run after each extraction step.
  • After step 2, manually exercise login + one read endpoint through the gateway before extracting anything.
  • After each extraction (3–7), re-run the full Postman collection against the gateway, and click through login, vitals entry, appointment booking, and the MediAssist chat in the running frontend.
  • After step 6, trigger an appointment confirmation and confirm an alerts row appears via RabbitMQ, not a direct DB write.
  • Final pass: docker-compose up, run the test suites, manual click-through of the full app.

Known limitations / explicitly out of scope

  • Single MySQL instance remains a single point of failure / scaling bottleneck — accepted tradeoff for this project's scope.
  • Auth token revocation list (auth.py:36, in-memory) stays single-instance since auth-service is one container; would need Redis if ever scaled horizontally.
  • Admin's cross-domain statistics becomes REST fan-out (synchronous), not event-sourced — fine at this scale, but not real-time like a proper read-model.
